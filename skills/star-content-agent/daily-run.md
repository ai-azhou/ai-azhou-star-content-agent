# 每天运行

定时任务到点，或者用户说「今天的 3 条」时，按这个顺序做。全程守 SKILL.md 的硬规矩；所有访问平台的命令都经过门卫。

**顺序是「先挑后读」**：先用库里已经读过的内容挑选、确认、交付；交付之后，再去读新收藏，留给明天用。这样推送能准时，用户开口要时几分钟就能拿到；就算今天读新收藏时出了问题，也不影响今天这一份。

## 没人在看时（定时任务启动的运行）

- 凡是需要用户动手的事（重新登录、打开 Chrome、启用扩展、处理验证码、回答问题），都不要等。把原因和用户要做的那一件事，写在当天 picks 文件的最上面（「需要你做的一件事：……」），再按推送方式通知用户，然后继续能做的部分，或者结束。
- 截图是黑屏时不要切到前台：这一条只读文字，在 gaps 里写「后台截图黑屏」。
- 设置还没做完（`setup.next_step` 不是 `done`）：不进设置流程，只在 `picks/今天日期.md` 里写一句「设置还没做完，请打开你的 Agent，发叫醒口令」，通知用户，然后结束。

## 步骤

1. **能不能跑。** 先按顺序检查下面几项：
   - 数据目录里有 `STOP` 文件：直接结束。
   - state.json 的 `paused_until` 还没到：直接结束。用户在对话里的，就告诉他还在暂停。
   - 加锁：运行 `门卫 lock <run_id>`，run_id 用「日期-时分」。
     - 返回 15，说明另一次运行正在进行。用户在对话里的，告诉他「正在跑，好了会给你」；没人在看就直接结束。
     - 锁是 3 小时以前留下的，才可以用 `--take-stale` 接管。
   - 今天已经交付过（`last_delivery.date` 是今天，按用户的时区算）：用户在对话里的，直接把今天的 picks 文件给他，然后解锁结束。用户明确说「重新挑」，才只重做第 4–6 步。没人在看就解锁结束。
2. **清理。** 删掉 `<数据目录>/tmp/` 里的文件，只删这个文件夹里的，用完整路径。
3. **看平台状态。** 运行 `门卫 status`。在暂停期的平台、`status` 记成 `blocked` 的平台，今天都不访问。
4. **挑选。** 按 `pick.md` 挑，只用库里的摘要，不读原文。得到这次用到的全部条目，记为 `selected_ids`。
5. **推送前确认还在。** 对 `selected_ids` 里的每一条，各打开一次，只看能不能打开，不重新读内容：
   1. `门卫 <平台> open "<最新的链接>" --session sca-check`；
   2. `门卫 <平台> eval @page-check --session sca-check`；
   3. 读完一条就关掉标签页，再开下一条。

   按看到的情况处理：
   - **正常打开**：availability 记 ok，更新 last_check。
   - **页面明确说内容不存在、已删除、无法浏览**（小红书常见「页面不见了」「笔记不存在」「无法浏览」，以 site-notes.md 为准）：availability 记 deleted，换候选里同一栏能用的下一条，整份最多换 2 次。换了以后，那一栏的说法、原话、链接要重新整理。
   - **说不清**（加载失败、旧链接打不开，但不是风控）：availability 记 unknown，写上原因。这一条照常推送，后面注一句「原帖暂时打不开，可能已被隐藏或删除」。
   - **碰到风控**：按硬规矩 3 暂停这个平台，剩下的确认都不做，也不为了确认去换别的条目。这个平台上没确认的条目照常推送，统一注一句「今天没有回原帖确认（平台暂停访问中）」。
   - **登录页**：按硬规矩 4 处理，这个平台剩下的也不再确认。
   - 平台本来就在暂停期，跳过确认，同样注一句「今天没有回原帖确认（平台暂停访问中）」。
6. **交付。**
   - 写成 `picks/年-月-日.md`，日期按用户的时区。格式见 pick.md 第四节。
   - 按 `prefs.delivery` 交给用户：用户在对话里就直接回复；没人在看就存文件，再发本机通知。
   - 交付成功后才做这几件事：在 `selected_ids` 每一条的 picked 里记上今天；更新 `last_delivery`。
   - 通知发不出去：文件留着，在 run.log 里记「通知失败」，下次用户开口时先告诉他。
7. **读新收藏，留给明天。** 对今天没暂停、没 blocked 的平台：
   1. **拉新收藏**：照 site-notes.md 从收藏夹入口打开，从上往下看。
      - 列表顺序已经确认过（`order_verified` 为 true）：连着碰到 5 条库里已有的，就不用再往下翻了。
      - 没确认过：最多翻 3 批。
      - 库里没有的写进去，first_seen 记今天；命中 skip.txt 的只记 id 和 skipped。
      - 库里已有的，更新 url、url_seen 和 last_seen。
   2. **不要自动判「取消收藏」。** 今天没看到某条，不代表用户取消了收藏：列表可能重排，也可能只看了一段。只有某次翻列表翻到了底、确定完整，而且库里某条不在里面，才把它的 membership 记成 unsaved；以后再看到它，就改回 saved。
   3. **页面和 site-notes.md 对不上时**，按顺序排除：
      1. 有风控迹象：按硬规矩 3；
      2. 是登录页：按硬规矩 4；
      3. 收藏列表确实是空的：在 picks 里提醒用户看一眼，不改库；
      4. 页面上明明有收藏，只是照笔记读不出来：才算网站改版。

      改版时重新摸一次读法，最多再用 5 次请求。摸出来了就更新 site-notes.md，在 run.log 里记一笔。摸不出来就停下这个平台，在下一份 picks 里告诉用户「网页改版了，我暂时读不到新收藏」。连续 3 天都摸不出来，就不再自动试，等用户说「再试试」。
      改版后库里的条目一条都对不上时，说明是读法变了，不是用户取消了收藏：这一次不改任何条目的 membership，也先别把它们当新收藏入库。
   4. **读内容**：按 `read-one.md` 读，名额看 state.json 的 `prefs`。
      - 新收藏和旧收藏分开算，新的先读；读不完的留在队列里，下次接着读。
      - 失败的记次数，连续失败 3 次的先跳过。
      - 每一条写进库以后，才能往前推进度。
8. **收尾。**
   - 在 run.log 里记一行：日期、run_id、结果（成功 / 部分完成 / 需要用户 / 环境不可用 / 碰到风控）、新增几条、读了几条（其中看了图或视频的几条）、确认了几条、请求总数（看 `门卫 status`）；
   - 关掉自己开的标签页；
   - 清空 `tmp/`；
   - 更新 state.json 的 `last_run`；
   - 运行 `门卫 unlock <run_id>`。

   中途出错也要做完这一步再结束。

## 补充

- **用户在对话里开口要（不设定时的用户）**：交付之后问一句「要不要顺便读一下今天的新收藏？大约 X 分钟」，用户同意才做第 7 步。
- **电脑睡着、关机错过的运行**：不补跑以前的日期，醒来后最多跑一次当天的。
